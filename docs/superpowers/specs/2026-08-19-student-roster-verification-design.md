# 학생 명단 대조 기반 대여 자격 검증 — 설계 문서

**작성일:** 2026-08-19
**상태:** 승인됨 (구현 계획 작성 대기)

## 배경 및 문제

현재 대여 신청은 신청자의 신원을 전혀 검증하지 않는다. 이름·학번·전화번호·학년을 입력받는 대로 신뢰하며, 그 결과 세 가지 문제가 있다.

1. **외부인 신청 가능** — 학과 학생이 아닌 사람도 임의의 학번으로 신청할 수 있다.
2. **학년 제한 무력화** — `src/components/rental/RentalForm.tsx`에서 학생이 학년을 버튼으로 직접 선택한다. 서버(`src/app/actions/rental.ts`)는 "선택 학년 >= 기자재 `minGrade`"만 검증하므로, 1학년이 3학년 버튼을 눌러 3학년 전용 장비(예: 소니 FX3)를 신청할 수 있다. 규정 제5조의 학년 구분이 실질적으로 동작하지 않는다.
3. **대여 제한(패널티) 회피 가능** — `RentalRestriction`은 학번 기준으로 차단하는데 학번이 검증되지 않으므로, 제재 대상자가 학번을 바꿔 신청하면 통과한다.

## 목표

학과 명단에 등재된 학생만 대여를 신청할 수 있게 하고, 학년을 명단 기준으로 판정해 위 세 문제를 함께 해소한다.

## 비목표 (Non-goals)

- **본인 사칭 방지 없음.** 같은 과 학생이 다른 학생의 학번·이름을 사용하는 경우는 차단하지 않는다. 이는 의사결정으로 확정된 범위이며, 필요해지면 이후 학교 이메일 OTP 등을 명단 위에 추가 레이어로 얹는다.
- **학생 로그인 계정 없음.** 명단은 인증 수단이 아니라 대여 자격 원장이다. 비밀번호·세션을 만들지 않는다.
- 기존의 조회용 비밀번호 방식(신청번호 + 비밀번호)은 그대로 유지한다.

## 방안 선택 근거

필요한 판정은 "우리 과 학생인가"와 "몇 학년인가" 두 가지이고, 이 답을 가진 출처는 학과 명단뿐이다.

| 방안 | 학과 소속 판정 | 학년 판정 | 현실성 | 결론 |
|---|---|---|---|---|
| 명단 대조 | 가능 | 가능 | 즉시 | **채택** |
| 학교 이메일 OTP | 불가(전교생 통과) | 불가 | 발송 인프라·비용 | 명단 없이 무의미 |
| 학과 공용 초대코드 | 유출 시 무력 | 불가 | 즉시 | 추적 불가 |
| 학교 SSO | 가능 | 부분적 | 학교 IT 협조 필요 | 학과 단위로 비현실적 |

어떤 방안을 택하든 명단은 필요하므로, 명단 대조를 기반으로 삼는다.

## 데이터 모델

```prisma
model Student {
  studentId  String   @id      // 학번. 정규화(trim) 후 저장
  name       String            // 이름. 원본 표기 그대로 저장
  grade      Int               // 1 | 2 | 3 — 학년 판정의 권위 있는 출처
  className  String?           // 반 (명단에 있으면 저장, 없으면 null)
  status     String   @default("active")  // active | inactive
  source     String   @default("upload")  // upload | manual
  updatedAt  DateTime @updatedAt

  @@index([status])
}

model StudentRosterUpload {
  id           Int      @id @default(autoincrement())
  fileName     String
  totalRows    Int      // 파일에서 파싱된 유효 행 수
  added        Int
  updated      Int
  deactivated  Int
  uploadedBy   Int?     // 관리자 id
  createdAt    DateTime @default(now())
}
```

설계 결정:

- **`studentId`가 기본키.** 학번은 학내 유일값이므로 별도 surrogate key가 필요 없고, 조회가 항상 학번 기준이다. 동명이인은 학번으로 구분되므로 문제되지 않는다.
- **삭제하지 않고 `inactive` 처리.** 졸업·휴학생을 삭제하면 과거 대여 이력의 학번 참조가 의미를 잃고, 잘못된 업로드를 되돌릴 수 없다. `RentalRequest`와 FK로 묶지 않고 학번 문자열로 느슨하게 연결한다(기존 구조 유지).
- **`source` 구분.** 업로드로 들어온 학생과 관리자가 개별 추가한 학생을 구분해 감사에 활용한다. 단, 비활성화 규칙은 양쪽에 동일하게 적용한다(아래 참조).

## 정규화 및 매칭 규칙

`src/lib/roster.ts`에 순수 함수로 분리한다(DB 접근 없음, 단위 테스트 대상).

- `normalizeStudentId(raw)` — 앞뒤 공백 제거. 그 외 문자는 보존한다(학번 체계 변경에 대비해 숫자 강제 변환은 하지 않는다).
- `normalizeName(raw)` — **모든 공백 제거** 후 비교용 문자열 생성. "홍 길동"과 "홍길동"을 같게 취급한다. 저장은 원본 표기를 유지하고, 비교 시에만 정규화한다.
- `namesMatch(a, b)` — 정규화한 두 이름의 완전 일치 여부.

## 신청 시 검증 흐름

학생이 신청하는 **살아 있는 진입점 3곳**에 공통 검증을 적용한다. 호출처를 확인해 확정한 목록이다.

| 서버 액션 | 파일 | 호출 컴포넌트 |
|---|---|---|
| `createRentalRequest` | `src/app/actions/rental.ts` | `RentalForm.tsx` (기자재 단건) |
| `createBatchRentalRequest` | `src/app/actions/rental.ts` | `CartPageClient.tsx` (장바구니 일괄) |
| `createClassroomRentalRequest` | `src/app/actions/classroomRental.ts` | `ClassroomRentalForm.tsx` (강의실) |

관리자 전용 액션(`createTestRentalRequest` 등)은 관리자 인증을 이미 거치므로 제외한다.

**죽은 코드 제거 (이 작업에 포함):** `src/app/actions/classroom.ts`의 `createClassroomRequest`와 이를 호출하는 `src/components/classroom/ClassroomForm.tsx`는 **어느 페이지에서도 import되지 않아 도달 불가능**하며, 대상 테이블 `ClassroomRequest`도 0행이다. 검증되지 않는 신청 경로를 남겨두면 향후 되살아났을 때 우회로가 되므로 두 파일을 삭제한다. `ClassroomRequest` 모델 자체 제거는 이 작업 범위 밖으로 두되(빈 테이블이라 무해), 별도 정리 대상으로 기록한다.

검증 순서:

```
학번 정규화 -> Student 조회 (status = 'active')
  |- 레코드 없음     -> 차단: "명단에 등록되지 않은 학번입니다. 학과 사무실에 문의해 주세요."
  |- 이름 불일치     -> 차단: "학번과 이름이 일치하지 않습니다."
  |- 통과           -> grade를 명단 값으로 덮어씀 (클라이언트가 보낸 학년 값은 폐기)
```

검증은 기존 대여 제한자(`getActiveRestriction`) 확인 **직전**에 배치한다. 존재하지 않는 학생에 대해 제한 조회를 수행할 이유가 없기 때문이다.

`grade`를 명단 값으로 덮어쓰는 것이 이 설계의 핵심 보안 효과다. 이후 기존 `minGrade` 검증 로직은 변경 없이 그대로 동작하며, 신뢰할 수 있는 학년 값을 받게 된다.

## 신청 화면 변경

- **학년 선택 UI 제거.** 학년은 더 이상 학생이 정하는 값이 아니다. `RentalForm.tsx`의 학년 버튼 그룹과 관련 상태(`grade`, `gradeInsufficient`)를 제거한다.
- **자격 확인 표시 추가.** 학번·이름을 모두 입력하면 서버에 확인을 요청해 `확인됨 · 3학년` 배지를 표시한다.
- **확인 API 응답은 최소 정보만.** `{ valid: boolean, grade?: number }`만 반환하며 **이름은 절대 반환하지 않는다.** 학번만으로 이름을 조회할 수 있으면 개인정보 유출이 된다. 학번과 이름이 모두 일치해야 응답하므로 학번 단독 조회 오라클이 되지 않는다.
- **rate limit 적용.** 기존 `src/lib/rate-limit.ts`를 사용해 학번·이름 조합 대입 시도를 제한한다.
- 학년 미달 시 안내는 제출 시점의 서버 오류 메시지로 처리한다. 기자재 목록·상세에 이미 "3학년 이상" 배지가 있으므로 사전 인지가 가능하다.

## 관리자 명단 관리 (`/admin/students`)

기존 관리자 레이아웃과 사이드바 패턴을 따른다.

**기능:**

- 명단 목록 — 학번·이름 검색, 학년·반·상태 필터
- 파일 업로드 — xlsx/csv, **미리보기 후 확정하는 2단계**
- 개별 학생 추가 — 학번·이름·학년·반 입력 (편입·복학생 즉시 등록용, `source='manual'`)
- 개별 비활성화 / 복원

**업로드 정책 — 전체 교체:**

최신 명단을 진실로 간주한다.

- 파일에 있고 DB에 없음 -> 추가
- 파일에 있고 DB에도 있음 -> 이름·학년·반 갱신, `status='active'`로 복원
- 파일에 없고 DB에 `active` -> **`inactive`로 변경** (삭제하지 않음)

`source='manual'`로 추가된 학생도 동일 규칙을 적용한다. 예외를 두면 졸업생이 영구히 남아 규칙이 예측 불가능해진다. 대신 미리보기에서 비활성화 대상을 모두 보여주므로 관리자가 확인 후 결정할 수 있고, 정상 운영에서는 다음 학기 명단에 편입생도 포함되므로 문제되지 않는다.

## 업로드 안전장치

전체 교체 방식은 잘못된 파일 하나로 전교생을 신청 불가 상태로 만들 수 있다. 확정 전에 반드시 차단한다.

- **컬럼 인식 실패 시 업로드 거부.** 학번·이름·학년을 식별하지 못하면 진행하지 않는다(반은 선택).
- **유효 행 0건이면 거부.**
- **변경 요약을 확정 전에 표시** — `추가 12명 · 갱신 3명 · 비활성화 예정 47명` 형태. 비활성화 대상 목록도 확인 가능해야 한다.
- **대량 비활성화 경고** — 비활성화 예정 인원이 기존 `active` 인원의 **50%를 초과하면** 경고를 띄우고 명시적 재확인을 요구한다.
- **업로드 이력 기록** — `StudentRosterUpload`에 파일명·시각·요약·작성자를 남긴다.

미리보기 단계는 DB를 변경하지 않는다. 파싱과 diff 계산만 수행하고, 확정 시에만 트랜잭션으로 반영한다.

## 파일 파싱

- 지원 형식: **xlsx, csv**
- 파싱 위치: **서버**. 클라이언트 파싱 결과를 신뢰하지 않는다.
- 헤더 인식: 컬럼 순서에 의존하지 않고 헤더명으로 매핑한다. 허용 표기 예 — 학번/학번호/student_id, 이름/성명/name, 학년/grade, 반/분반/class
- 빈 행과 헤더 위쪽 여백 행은 건너뛴다.
- 라이브러리: `exceljs` 추가 (프로젝트에 엑셀 파서가 없음)

## 개인정보 취급

- 저장 항목은 **학번·이름·학년·반**으로 한정한다. 전화번호·이메일·주소는 명단에 저장하지 않는다.
- 접근은 관리자 인증 필수(`requireAdmin`).
- 공개 API는 이름을 반환하지 않는다(위 "신청 화면 변경" 참조).
- 저장 범위가 학과가 이미 보유한 정보를 넘지 않는다.

## 오류 메시지

| 상황 | 메시지 |
|---|---|
| 명단에 없는 학번 | 명단에 등록되지 않은 학번입니다. 학과 사무실에 문의해 주세요. |
| 학번은 있으나 이름 불일치 | 학번과 이름이 일치하지 않습니다. |
| 비활성(휴학·졸업) 학생 | 명단에 등록되지 않은 학번입니다. 학과 사무실에 문의해 주세요. |
| 확인 요청 과다 | (기존 rate limit 메시지 재사용) |

비활성 학생과 미등록 학생에 같은 메시지를 쓰는 것은 의도적이다. "이 학번은 존재하지만 휴학 상태"라는 정보를 외부에 노출하지 않는다.

## 테스트 전략

**단위 테스트 (`src/lib/roster.ts`)** — 기존 vitest 사용

- `normalizeStudentId` — 앞뒤 공백 제거, 내부 문자 보존
- `normalizeName` — 공백 제거("홍 길동" = "홍길동"), 빈 문자열 처리
- `namesMatch` — 일치/불일치/공백 변형
- diff 계산 — 추가·갱신·비활성화 분류가 정확한지, 빈 파일·전체 교체 경계 조건

**파서 테스트**

- 컬럼 순서가 다른 파일, 헤더 표기 변형, 빈 행 포함, 헤더 위 여백 행
- 필수 컬럼 누락 시 거부되는지

**통합 확인 (수동)**

- 명단에 있는 학생 -> 신청 성공, 학년이 명단 값으로 기록됨
- 명단에 없는 학번 -> 차단
- 이름 불일치 -> 차단
- **1학년 학생이 3학년 전용 장비 신청 -> 차단** (기존 구멍이 막혔는지 확인)
- 업로드 미리보기 -> 확정 전 DB 무변경 확인
- 50% 초과 비활성화 시 경고 동작

## 배포 시 주의

명단이 비어 있는 상태로 검증이 활성화되면 **모든 학생의 신청이 차단된다.** 배포 순서를 지켜야 한다.

1. 스키마 반영 및 관리자 명단 관리 화면 먼저 배포
2. 관리자가 명단 업로드 및 확인
3. 신청 검증 활성화

구현 계획에서 이 순서를 태스크로 분리한다.
